# 暗区突围 · 武装派遣自动刷新

按规则表（Excel，默认 `工作簿1.xlsx`，也可用 `DARKZONE_RULES` 指定路径）校验「武装派遣」里的装备词条，不一致就点刷新，一致就停手。
**只刷词条，绝不点「派遣」**——派遣由人工点。

## 项目解决什么问题

「暗区突围（Arena Breakout）」的「武装派遣」里，每刷新一个装备槽位都要扣 500 刷新券。
想刷出规则表里那件想要的装备，纯靠手动点又慢、又容易看错词条、还常白花券。
这个脚本把「读规则表 → 识别详情页三行装备 → 判断在不在池内 → 不在就点 ↻ 刷新 → 命中就停手」
整条链路自动化，省屏省券，并且每次点击都落日志，出问题可逐笔倒查。

它**只负责刷词条**：三行装备都命中规则池之后自动停手，**绝不点「派遣」**——派遣这最后一步
（花钱/派出去、不可逆）始终留给你手动点。

## 主要功能

- **数据驱动**：装备「该不该刷」完全由桌面 Excel 规则表决定（每个槽位一张可选装备池 + 排除名单），改规则不改代码。
- **自动识别详情页三行装备**：adb 截屏 + OCR，按「点击装备」标签锚定每一行，坐标自动换算（图片像素 → 真机像素）。
- **双 OCR 引擎**：默认 Windows 自带 OCR（零依赖，每屏 1.2–1.7 s，常驻 worker 后 0.25–0.35 s）；可选 RapidOCR（更准，每屏 7–11 s）。
- **命中即停、不在池就点 ↻**：每个槽位独立判定，不在池内的那一行才点刷新，已在池内的跳过（0 次点击）。
- **只刷详情页**（默认 `detail_only`）：不是「武装派遣」详情页就一步都不走；旧「列表页起步」流程需 `--allow-list`。
- **一整套写死的安全阀**：dry-run 默认、派遣禁点区、竖屏保护、刷新确认框白名单、行锚定、点击无变化检测、
  重读安全网、花券前再确认、时间闸门、收尾补确认（详见下方「安全阀」）。
- **消费台账 + 结尾摘要**：每次刷新记 500 券、跨次累计，跑完打印本次/累计刷新次数与券数。
- **可选提速**：ffmpeg 视频流取帧，真机一次刷新 ≈2.4 s（找不到 ffmpeg 自动退 gzip，≈5.4 s）。

## 安装

1. **系统**：Windows 10/11（OCR 走系统自带 `Windows.Media.Ocr`，离开 Windows 环境无法用）。
2. **Python ≥ 3.10**，装核心依赖：

   ```powershell
   pip install openpyxl Pillow
   ```

   可选更准的 RapidOCR 后端（模型打进 whl，不用另拉模型）：

   ```powershell
   pip install -i https://pypi.tuna.tsinghua.edu.cn/simple rapidocr-onnxruntime==1.4.4
   ```

3. **真机额外需要 adb**（`adb devices` 能列出设备即可）；**可选 ffmpeg**（视频流提速，设环境变量
   `DARKZONE_FFMPEG` 指向它，找不到会自动退 gzip 不影响正确性）。

## 使用方法

从项目根目录执行（`profiles/default.json` 按包内相对路径解析）。**默认 dry-run：不带 `--live` 就只读屏算坐标、一次都不点**。

| 场景 | 命令 |
|---|---|
| 离线预演（无手机、不点击） | `python -m darkzone.runner --image samples\live_detail.png --device 3200x1440 --rules 规则表.xlsx` |
| 真机 dry-run（读真机、算坐标、不点击） | `python -m darkzone.runner --rules 规则表.xlsx` |
| 真机 live（真正点 ↻） | `python -m darkzone.runner --live --rules 规则表.xlsx` |

真机前置：手机插 USB → 开「USB 调试」→ `adb devices` 能列出设备 → 游戏横屏停在「武装派遣」**详情页**。
`--rules` 默认读当前目录 `工作簿1.xlsx`，也可设 `DARKZONE_RULES` 环境变量覆盖；显式给它最省心。
完整参数（`--limit` / `--ocr` / `--capture` / `--fast-confirm` / `--no-sweep` …）见下方「怎么跑」。

## 怎么跑

| 想干什么 | 命令 |
|---|---|
| 只看不动（推荐先跑） | 双击 `dry_run.bat` —— 只读屏、算坐标、打印计划，一次都不点 |
| 真机开刷 | 双击 `run_live.bat` —— 真正点击；默认每行最多 40 次；改次数：`run_live.bat --limit 20` |
| 换准一点的 OCR（慢 7 倍） | 双击 `run_ocr_rapid.bat`，或加 `--ocr rapid`（默认 `auto`/`win` = 系统 OCR，快） |
| 拿现成截图预演 | `python -m darkzone.runner --image samples\screen2_refresh_entries.jpg` |
| 旧的「列表页起步」流程 | 加 `--allow-list`（默认关闭，见下） |
| 调速度 | `--wait-tap 0.25 --wait-screen 0.55`（点击后等多久）、`--capture {auto,gzip,fast,png,stream}`（默认 auto = 先常驻视频流、起不来退设备端 gzip、再原始帧、最后 PNG；`stream` 路读一屏 0.01 s、一次刷新 ≈2.4 s，见下）、`--read-retries 8`（画面没变时多读几次）、`--settle-reads 2`（词条画稳了再判，stream 默认 2）、`--settle-guard 0.9`（点完「确定」先睡过动画窗口再信任何一帧，`0` = 关，见下）、`--confirm-reads 2`（花券前再确认几次，防流帧噪声白花 500 券，stream 默认 2）、`--fast-confirm`（盲点「确定」快路，默认关；**2026-10-11 实测后不建议开**——弹窗 ~1–2 s 才出来而盲点只等 0.7 s，常点空反而更慢，见下）、`--no-flush-pending`（关掉「收尾补确认」，默认开，见「安全阀」；关掉会把最后一轮的确认框留给人工）；`set DARKZONE_OCR_WORKER=0` 可关掉常驻 OCR worker（默认开，见下） |

真机前置：手机插 USB → 打开「USB 调试」→ 弹窗点「允许」→ `adb devices` 能列出设备
（`run_live.bat` 会最多等 60 秒；想要别的时间用 `--wait-device 120`）。
**先在手机上手动点「选择」进入「武装派遣」详情页**，再跑脚本。

## 它每一步在干什么

**默认只管详情页**（用户 2026-10-11 的决定：「暗区首领那一栏彻底不管」「这条刷完就停手，我手动点派遣」）：

1. 读当前这一屏：不是「武装派遣」详情页（比如停在派遣列表）就一步都不走，直接报错让你手动进页面；
2. 详情页：规则表每个槽位对着右侧一行装备 → 已在池内就跳过、不在就点该行 ↻
   → 命中即停该行、转下一行；
3. 三行都就绪 → 停手 + 打印摘要 + 写出报告（`logs\run_*.json`）；**不点「派遣」，也不去找下一条**。

需要时才用 `--allow-list` 走旧流程（界面1 列表：读「暗区首领」→ 名字在排除名单里就点该栏 ↻ →
点「选择」进详情）；这条路默认关闭，因为它会动到「暗区首领」那一栏。

## 安全阀（都写死了，不用配置）

- `dry_run` 默认开：不显式加 `--live` 就绝不点击；
- **派遣保护**：任何落点离「派遣」按钮 3% 屏宽以内、或落进「派遣」矩形的禁点区，直接拒绝并报错退出；
- **竖屏保护**：截到竖屏（游戏没横过来/不在前台）直接报错，不瞎点；
- **刷新确认框**：真机上点 ↻ 必弹「提示 / 是否刷新特殊条件：xxx / 确定」模态框。只有正文含「刷新」、且不含 派遣/提交/出售/购买… 的弹窗才自动点「确定」（这种点击算生效，不会被误判成「点了没变化」）；点完确定弹窗还在 → 报错停手；
- **行锚定**：详情页按每行「点击装备」标签反推锚点取行（装备名在其上方 ≈7.2% 屏高）。解析出的行数 ≠ 槽位数就重读一次，仍不对 → `row_count_unexpected` 停手——**绝不猜着点**，因为行错位会刷错行、白花券；
- **「点了没变化」检测**：连续 3 次点击后全屏文字毫无变化（含顶栏资源数字）→ 判为点歪/有弹窗/资源不足，报错停止，不硬刷；
- **重读安全网**（2026-10-11 提速时加）：等待压短后可能读到「游戏还没把新画面画出来」的旧帧。读到既不是弹窗、文本签名又和点之前一样时，先按 `read_retry_delay` 每 0.7 秒重读一次、最多 8 次（≈5.6 秒，**画面一变就立刻停**），确认真的没变化才回去走扫描兜底——没有这层，读早了会被误判成「点空了」，扫描再点一次就白花 500 券。点「确定」之后同样重读（否则会误判弹窗还在 → 整轮 abort）；
- **花券前再确认**（2026-10-11 深夜加，`--confirm-reads`，`capture=stream` 时自动取 2）：点 ↻ 之前必须**连续**读到「这一行不在池内」才动手。起因是真机事故——视频流帧把 `AUG突击步枪` 读成 `AIJG突击步枪`（h264 糊了小字），模糊匹配对 3 个字母的核心容不下这种错，于是把**本来已经在池内**的一行判成「不在池内」，白刷一次花 500 券。多读一帧在流路上只要 0.01 s；读回来发现在池内就直接跳过并记 `confirm_in_pool`；
- **扫描兜底**：点 ↻ 没反应时按 `profiles\default.json` 的偏移量扫附近坐标，最多再试 2 个点（坐标已按真机像素核对过，不允许无限连点烧券）；
- **时间闸门 `settle_guard`**（2026-10-11 深夜加，默认 0.9 s，`--settle-guard 0` 可关）：真机是「顶栏先扣券 → 新词条过一会儿才画出来」，而流路读一帧只要 0.01 s，所以点完「确定」立刻读到的还是**刷新前的旧画面**；旧画面的读法和点前那次不一样（都是噪声），于是「签名变了 + settle 稳定」双双被骗过 → 把旧词条当成刷新结果（事故与死路见下）。规则：点了「确定」且这一屏走的是多读的取屏路时，先睡过动画窗口再读第一帧。**闸门挂在「点确定」这个动作里**（`_handle_dialog` + 盲点分支），不挂在调用点——17:21 那次真机验证就是挂错地方导致闸门一次没跑（见下）；
- **收尾补确认 `flush_pending`**（2026-10-11 深夜加，默认开，`--no-flush-pending` 可关）：一轮的**最后一次** ↻，确认框常在工具收尾之后才画出来（弹窗要 ~2 s），于是「券扣了、行没提交」——下一次启动会看到模态框而直接 abort（真机 `--limit 40` 第一次就是这么被挡下的）。规则：出报告之前多读一屏（`final_peek`），若还挂着**刷新确认框**就补点「确定」（这笔刷新本来就点过、钱也记了）并按补确认之后的真实词条**重判那一行**（原来那轮读到的可能是刷新前的旧行）；不是刷新框就只记 `pending_dialog_left`，交给人工，绝不自动点别的框。日志事件 `pending_dialog` / `final_recheck` / `pending_dialog_left`，报告里也会写 `pending_dialog`；
- 每次点击前后都留截图 + `logs\events.jsonl` 事件流，出问题按日志倒查。

## 组成

| 文件 | 作用 |
|---|---|
| `darkzone\rules.py` | 读规则表 → 规则块 / 装备池 / 排除名单 / 校验（`validate`） |
| `darkzone\ocr_match.py` | OCR 文本归一化 + 两道门控匹配（核心前缀按「带字类权重的编辑代价」判、类别尾巴必须**紧跟核心之后**），防止池外装备被误判成池内件 |
| `darkzone\win_ocr.ps1` / `win_ocr_worker.ps1` / `win_ocr.py` | 用 Windows 自带 OCR（zh-Hans-CN），不依赖任何第三方库。`win_ocr_worker.ps1` 是**常驻 worker**（引擎只加载一次，一行请求一行回答），默认走它：每屏 **0.25–0.35 s**；worker 不可用时自动回退 `win_ocr.ps1` 一次性进程（**0.9–1.2 s**），`DARKZONE_OCR_WORKER=0` 可强制走老路 |
| `darkzone\rapid_ocr.py` | RapidOCR（PP-OCRv4，onnxruntime，装在项目 `.venv`）后端，**每屏约 7–11 秒但更准**，接口和 `win_ocr` 完全一样 |
| `darkzone\ui.py` | 界面解析：列表页三栏 / 详情页三行 + 坐标换算（图片像素 → 真机像素）+ 跨引擎的标题合并 |
| `darkzone\runner.py` | 两段式主循环 + 安全阀（`python -m darkzone.runner`）；`--ocr {auto,rapid,win}` 选识别后端，`--wait-tap/--wait-screen/--read-retries/--capture` 调速度 |
| `darkzone\adb.py` / `source.py` / `stream.py` | adb 控制层（`screencap` 设备端 PNG / `screencap_fast` 原始帧+本地 JPEG / `screencap_gz` 设备端 gzip+本地解压）/ 屏幕来源抽象（真机 = LiveSource，`auto` 链 = stream→gzip→raw→PNG 逐级回退，离线 = ImageSource）/ `FrameStream` 视频流取帧（常驻 `screenrecord` + ffmpeg，读一屏 0.01 s；`LiveSource.last_chain` 记这一屏实际走的档，runner 靠它决定多读几次） |
| `darkzone\fake_screens.py` | 离线假手机：合成同版式截图 + 热区状态机 |
| `samples\ocr_rows_rapid.json` | **固化的真实 OCR 行**（两张真机截图 + 合成图 × 两个引擎），换引擎回归用 |
| `profiles\default.json` | 比例坐标（↻ 横向 0.910 等）+ 扫描偏移 |

## 两个 OCR 引擎（2026-10-11 加）

| 引擎 | 怎么来的 | 每屏耗时（3200×1440，Core Ultra 5 125H 纯 CPU） | 特点 |
|---|---|---|---|
| Windows OCR | 系统自带 `Windows.Media.Ocr`，零依赖 | **1.2–1.7 s** | 中文准；汉字间会插空格、字母数字易错（`BT101`→`BTI01`、`SJ16`→`S」16`）——靠 `ocr_match` 的归一化兜住 |
| RapidOCR 1.4.4 | 项目 `.venv` 里 pip 装的 `rapidocr-onnxruntime`（PP-OCRv4 mobile，模型打进 whl，不用连 GitHub） | **7–11 s**（首次含加载模型 18 s） | 中文/字母数字都更准、不插空格（`BT101战术防弹衣` 直接读对）；代价是慢 7 倍 |

& ".\.venv\Scripts\python.exe" -m pip install -i https://pypi.tuna.tsinghua.edu.cn/simple rapidocr-onnxruntime==1.4.4

`--ocr` 三档（用户 2026-10-11 定：**默认用快的**）：

`rapid` = 项目 `.venv` 里的 RapidOCR（更准，每屏 7–11 s，用 `run_ocr_rapid.bat`）。

换引擎踩到的坑（已修，`darkzone\ui.py:merge_split_labels`）：同一句标题

## 一次刷新要花多久（2026-10-11 提速，用户要求「缩短每次点击时间，加快每次运行速度」）

一次刷新 = 点该行 ↻ → 读屏（弹窗）→ 点「确定」→ 读屏（新词条）→ 校验，也就是 **2 次读屏**。实测拆解：

| 环节 | 旧 | 新 | 说明 |
|---|---|---|---|
| 取屏 | 设备端 PNG **2.30 s**（3.41 MB） | 设备端 `gzip -3` 压原始帧再传 = **1.39 s**（中位，见第 15 条） | 现在的默认路：`screencap \| gzip -3`（5.05 MB）→ 本地 `zlib` 解压 0.08 s → `PIL` 转 JPEG q90。旧快路 `Adb.screencap_fast`（原始帧 18.43 MB 直传 1.67 s + 转 JPEG 0.24 s = 1.91 s）降级为第二选择；三条路都失败才走设备端 PNG |
| 点击后等待 | 0.6 + 1.2 = **1.8 s** | 0.25 + 0.55 = **0.8 s** | 压短有风险（读早了会当成「点空了」），所以配了重读安全网 |
| OCR | 1.2–1.3 s | **0.25–0.35 s**（常驻 worker，2026-10-11 晚加，见下） | 慢的根源**不是**「扫了太多区域」，而是每次调用重付 ~0.6 s 的 powershell 进程启动 + WinRT 引擎加载：一张 **160×72** 的小图也要 0.54 s，全屏 0.87 s。改成常驻 worker 后全屏 0.27 s、右面板 0.13 s |
| **每次刷新合计** | **8.96 s**（跑#7：104 次刷新 932 s） | 默认路（流）**2.4 s 中位**；加时间闸门 ≈**3.3 s**（待真机复核）；`--capture gzip` 默认路 **5.42 s**；**带闸门的 `--fast-confirm` 反而 5.19 s（不建议开）** | 真机实测，数字取自 runner 自己的 `charge` 事件 `sec` 字段（10 次流路刷新的中位）；中间态 ≈7.5 s 是「新取屏/新等待但还没上 worker」那次试跑；`logs\_speed_ab.py` 量取屏、`logs\_cycle_time.py` 量周期 |

### 常驻 OCR worker（2026-10-11 晚，用户要求「转向 ROI 识别」时查出真凶）

用户的原话是「识别慢的根源往往在于扫描了太多无关区域」。实测把这个假设**否掉了**：耗时基本与面积无关，
固定开销才是大头 —— 所以真正该省的是「每次调用重新起一个 powershell + 重新加载 WinRT 引擎」。
做法：`darkzone\win_ocr_worker.ps1` 常驻一个进程（引擎只加载一次，一行请求一行回答），
`win_ocr.py` 默认走它，起不来或中途挂掉就自动回退老的一次性进程（还会打印一行 `[warn]`）。

| 场景（同一张真机截图，3200×1440） | 一次性进程 | 常驻 worker | 省 |
|---|---|---|---|
| 全屏 | **0.94–1.15 s** | **0.25–0.58 s** | 0.37–0.78 s |
| 全屏（跑 5 次的稳态，`start_162831_890.jpg`） | 1.04 s | **0.28 s** | **0.76 s（3.7×）** |
| 右面板整条 1280×1440（原型实测） | 0.70 s | 0.13 s | 0.57 s |
| 右面板三行 1280×748（原型实测） | 0.67 s | 0.07 s | 0.60 s |

* 启动成本只付一次：worker 首次调用（含起进程 + 加载引擎）**1.03 s**，之后每次 0.25–0.58 s；
* **结果必须逐字节一样**：`logs\_worker_check.py` 拿 8 张真机/合成图对比「行文本 + 坐标 + 判页 + 池内判定」，
  两边**完全一致**（`FAIL 0`）——同一张图、同一个引擎，本来就不该有差异，有差异就是协议有 bug；
* 关掉它：`$env:DARKZONE_OCR_WORKER="0"`（runner 的 `start` 事件会记 `win_ocr_worker` 状态，便于核对）；
* 提速效果：`test_runner_offline`（整套跑一遍要 OCR 几十次）**54.4 s → 18.2 s**；
* **真机复测（2026-10-11 晚，花 1000 券经用户批准）**：同一张真机图、同一个槽2（未命中池内护甲），
  runner 自己上报一次刷新 —— 默认两段读屏路 `charge.sec = 5.42`（旧 8.96 s 的 60%），
  `--fast-confirm` 盲点路 `charge.sec = 3.57`（旧默认路的 40%，约 2.5×）；
  两次 `done.elapsed_s` 分别 8.1 s / 6.1 s（含起进程、等设备、体检读屏一次）。

### ROI 裁剪：实测是死路（记下来免得以后再试）

在同一张真机截图上把图裁成「只留右面板三行」甚至「160×72 的极小图」测下来：

| 裁剪 | 面积 | 一次性进程耗时 | 说明 |
|---|---|---|---|
| 全屏 3200×1440 | 100% | **0.69 s** | 29 行 |
| 右面板三行 1280×748 | 21% | 0.63 s | 12 行（丢了 boss、顶栏） |
| 三行带 + 顶栏 3200×892 | 62% | 0.77 s | 该留的都留了 |
| 极小 160×72 | 0.25% | **0.54 s（0 行）** | 面积只剩 0.25%，耗时还有全屏的 78% |

上了 worker 之后再裁，收益进一步被「解码 + 裁剪 + 另存 JPEG」吃掉：真机图实测**只省 0.01–0.15 s**
（`logs\_roi_parse_check.py`）。而且裁剪有两个真实风险（同一脚本跑出来的）：

1. `live_detail_hdr.png` 裁剪后第一行 ↻ 的 y 从 296 抖到 **292**（版面分析变了，坐标不该变却变了）；
2. `live_dialog.png` 裁剪后把「确定」按钮裁掉，弹窗页被判成**列表页** —— 这是危险方向。

结论：**不做 ROI 裁剪**；要提速就砍「读屏次数」（`--fast-confirm`）或取屏本身（现在的大头是设备端 1.9 s）。


还想再快就只能砍读屏次数——**盲点「确定」快路**（`--fast-confirm`，2026-10-11 用户点头加、**默认关闭**）：
点完 ↻ 不读屏，等 `--wait-dialog`（默认 0.7 s）后直接点 profile 里量好的确认框坐标
（`dialog_confirm_xy_frac = [0.4975, 0.7167]`，即真机 (1592,1032)），然后只读一次屏拿新词条，
**每次刷新 ≈4 秒**。代价与兜底：

* 这条路**不看弹窗文字就确认**——万一 ↻ 弹出的是别的框（理论上没有，真机每次都是「是否刷新特殊条件」），也会被点掉；
* 只盲点一次：点完照样读屏，若读回来还是弹窗就回落到正常弹窗处理（重读 → 只放行含「刷新」的框）；
* 「派遣」禁点区照旧生效（(1592,1032) 离派遣按钮 1134px，不在禁点区里）；
* 没开这个开关时，行为与以前完全一样（两段读屏 + 弹窗文字检查）。
* 离线验证：假手机场景 **N**（`test_runner_offline.py`）断言盲点后**确实扣了 500 券**（说明「确定」真的点到）、槽1 只点一次 ↻、且**没有** `read_retry`（省的就是那次读屏）。
* **真机验证（2026-10-11，500 券）**：`--live --fast-confirm --limit 1` 下槽2 刷 1 次，
  事件流是 `tap slot2_refresh1`(16:28:34) → `fast_confirm`(1592,1032) → `tap slot2_refresh1_fastok`
  →（0.8 s 后）只读一屏 → `charge` 500 券 → `row_check` 新词条 `AL制式弹挂甲`(16:28:38)，
  **一次刷新 4 秒**，全程没有 `auto_confirm`、没有 `read_retry`，也没碰「派遣」；累计台账 139000 券。

### 视频流取帧 `--capture stream`（2026-10-11 深夜，用户选「从 scrcpy 视频流取帧」）

取屏的大头（设备端 gzip 1.39 s）本质是「每次都要重新压一张图再传 5 MB」。改成**常驻一条视频流**后，
读一屏只剩「拷贝一个已经写好的 JPEG」：

```text
adb -s <dev> exec-out "screenrecord --output-format=h264 --bit-rate 8M --time-limit 170 -"
        │  (h264 裸流)
        ▼
ffmpeg -f h264 -i - -vf fps=4 -q:v 5 -f image2 -update 1 -y logs\stream_frame.jpg
```

* 管道上**必须显式写 `-f h264`**：不写时 ffmpeg 在不可 seek 的管道上探不出格式，**一帧都不出且不报错**（踩过）；
* 代码在 `darkzone\stream.py`（`FrameStream`：`start/ensure/latest/stop/summary`），`LiveSource` 的链是
  `stream → gzip → raw → 设备端 PNG`，顺手失败只记一次 miss 并让这一屏退到下一档；
* **真机同屏 5 轮对照**（`logs\_stream_vs_gzip.py`，只读、0 券）：读一帧中位 **0.01 s**（gzip 1.3 s），
  三行齐全 5/5，用「红字像素带」量出的词条真实 y 与 gzip 路一致（297/521/745 vs 296/521/744）；
* 依赖外部 ffmpeg：`DARKZONE_FFMPEG` 环境变量 → PATH → 剪映自带的两份（`stream.py:FFMPEG_CANDIDATES`），
  都找不到就自动回退 gzip，不会报错；退出时 `stop()` 会 terminate 两个进程并 `pkill screenrecord`。

两个坑（都已修，且都留了回归夹具）：

1. **开头 ~1.5 s 是「坏帧窗口」**：刚起流的关键帧只有 ~154 KB（稳态 ~215 KB），实测**整行漏读第 1 行装备名**，
   而右侧面板表头「特殊习惯」被读成 `持殊习惯` 顶上来当第 1 行 → 三行 ↻ 变成 **400/522/624**（点错位置）。
   修法：`FrameStream.start(warmup=1.5)`：等满窗口、期间至少换过一帧；`darkzone\ui.py` 加
   `LABEL_FUZZY_MIN = 0.72` + `_fuzzy_detail_label()`，任何一个字之差的固定文案都不会被当成词条行。
   **窗口有多长是量出来的**（`logs\_stream_warm_sweep.py` → `logs\stream_warm_sweep_out.txt`，
   5 条新流 × 第一帧出现后每 0.25 s 取一帧判三行）：`t=0.00 s` 有坏的流 **5/5**
   （`KN复防弹衣`、`AIJG突击步枪`、`钢新星战木头盔`…），0.25 s 3/5、0.50 s 2/5、0.75 s 2/5、
   1.00 s 1/5、**1.50 s 0/5**。代价是每次起流多花 ~1.3 s（`start()` 2.6 s → 3.9 s，一轮只付一次）。
   这么修之后复测（`logs\_stream_warm_probe.py`，4 条新流）：`start()` 回来的第一帧 3/4 三行全对、
   再等一帧 3/4；稳态（`logs\_stream_fn_probe.py`，同一条流连读 15 帧）**15/15 帧三行全对**
   （改之前是 14/15），连续 3 帧都读错的组合 **0** —— 也就是说 `settle_reads` + `confirm_reads`
   这两道网几乎不需要开火。但坏帧是**随机**的（起流后仍可能碰到连续两帧读坏槽2），
   所以 confirm 网不能省：它兜住的代价最多是「白刷一次 500 券」，不会把池外判成池内。
2. **h264 会吃掉小字的笔画**：「点击装备」常被读成 `占击装备 / 击装备`（8M 与 16M、q1 与 q5 都一样，
   所以不是码率问题）→ 锚点扫描失效 → 几何兜底把按钮行当词条。修法：`is_tap_equip_label()`
   （`DETAIL_TAP_RE = [点占店]?击装备`）同时用于锚点扫描和 `parse_screen` 的判详情。
   词条名本身也会带噪声（`钢铁新星战木头盔`），由模糊匹配兜住（命中 `钢铁新星战术头盔`，score 0.95）。

* 夹具与回归：`samples\stream_first_frame.jpg`（退化首帧）、`samples\stream_steady.jpg`、
  `samples\gzip_detail_same_screen.jpg`，断言在 `darkzone\test_real_anchors.py`
  （首帧允许「行数不足」→ 交给 runner 的行数守卫重读/停手，但**绝不许**把固定文案当词条）；

### 时间闸门 `settle_guard`：点完「确定」别信动画中间帧（500 券买来的教训）

真机的刷新顺序是**顶栏先扣券 → 新词条过一会儿才画出来**。流路读一帧只要 **0.01 s**，
所以点完「确定」立刻读到的还是**刷新前的旧画面**。危险在于：旧画面的读法和点前那次读法
**文本不一样**（都是 OCR 噪声），于是「全屏签名变了」和「settle 两帧稳定」**双双被骗过**，
把旧词条当成刷新结果 —— `logs\live_stream_1.txt` 就是这么白花了 500 券：

```text
17:03:53 只读预演   槽1 = AUG突击步枪（在池内 ✓）
17:05:38 live 首读  槽1 = AIJG突击步枪（h264 糊字）→ 判池外 → 点 ↻ 花 500 券
17:05:4x 点完确定   读到的「AUG突击步枪」其实是**旧画面** → 工具误报「命中」
17:14:0x 下一次预演 槽1 = AN94突击步枪  ← 那次刷新真正抽到的东西，期间没有任何点击
```

**先试过文本比对，实测是死路**：`logs\_same_item_probe.py` → `logs\same_item_probe_out.txt`，
用 `canon` + `similarity` 量真机日志里的成对样本 —— 噪声对（同一件）最低分 **0.667**
（`AN9"4突击步枪` vs `AUG突击步枪`），真换件最高分 **同为 0.667**（`AN94突击步枪` vs `AUG突击步枪`）
→ **可分离间隙 = 0.000**，没有任何阈值能同时容下噪声又区分真换件（短字母枪名本来就长这样）。**别再试。**

**能用的只有时间**：`Config.settle_guard = 0.9`（CLI `--settle-guard`）。规则是「点了「确定」
且这一次走的是多读的取屏路（`eff_settle_reads() > 0`）时，**先睡过动画窗口**再读第一帧」；
`0` = 关（老行为，留给离线测试和 gzip 慢路 —— gzip 一帧 1.4 s，本来就慢过动画）。
顺带一条已有的规则也被这次事故确认了：**「确定」点过就说明券一定扣了**（`confirmed` 直接算 `changed`），
绝不再去扫描点第二次。

**闸门必须挂在「点确定」这个动作里**（真机 `logs\live_guard_1.txt`，17:21 那次验证暴露）：
第一次真机验闸门时 `settle_guard` 事件**一次都没出现** —— 点 ↻ 之后第一屏还不是弹窗
（顶栏先变、弹窗 ~2 s 才画出来），`_tap_wait_read` 里那句 `if kind == "dialog"` 没触发；
弹窗是**稳定性复读循环**里读到的（`settle reads 3 screen_kind dialog`），函数带着 `kind=dialog`
返回给调用方，调用方先记 `charge`，弹窗真正被确认发生在**下一轮 `_ensure_kind`** 里 ——
而闸门当时写在 `_tap_wait_read`、绑在 `confirmed` 上，于是整条被绕过（那次真机白跑 1000 券，
代价记在这里）。修法：闸门挪进 `Runner._handle_dialog`（**唯一**按「确定」的地方，两条确认路
都覆盖）与 `--fast-confirm` 的盲点分支（`_blind_confirm` 之后），两处都调 `_settle_guard_wait`。

* 离线场景 **R**（`anim_seconds=0.6` + `settle_guard=0.9`）：假手机把真正抽到的池外装备
  `M4A1突击步枪` 画出来，断言工具**看见了它**、再刷一次、共 1000 券、最终命中池内；
* 对照组 **R2**（同一台假手机但 `settle_guard=0`）：旧帧骗过工具 → 它只刷 1 次就报
  `ready=True`（「三行都在池内，可以派遣」），而假手机那一行其实是池外的 `M4A1突击步枪` ——
  **最坏的那种错**（不是白花券，而是「池外被当成池内」）就钉在测试里。
* 离线场景 **S/S2**（`dialog_delay_reads=2` 复刻「弹窗后弹、下一轮才确认」那条路）：
  **S**（`settle_guard=2.0` > 动画 1.5 s）断言 `settle` 事件里 `screen_kind=dialog`、闸门事件
  `why=dialog_ok`、只花 500 券；**S2**（同一台假手机、`settle_guard=0`）白花一次 = 1000 券 ——
  把「闸门挂错地方」这个 bug 本身钉进测试（把闸门挂回 `_tap_wait_read` 时 S 会 FAIL）。
* 代价：流路每次刷新 +0.9 s（≈2.4 → ≈3.3 s），仍明显快于 gzip 默认路 5.42 s。
* **`--fast-confirm` 现在不值得开**（真机 `logs\fc2_live.txt`，17:28）：弹窗要 ~1–2 s 才画出来，
  而盲点只等 `wait_dialog=0.7` s → 盲点经常**点空**，弹窗由 `_handle_dialog` 补点一次、闸门也跟着
  跑两遍（`why=blind_confirm` + `why=dialog_ok`）→ `charge.sec = **5.19 / 5.16**`，比普通路更慢。
  16:28 那次盲点正好点中（4 s、全程无 `auto_confirm`），所以它是个**赌**：要用就得把 `--wait-dialog`
  提到 ≥1.6 s，而普通路本来就更快 —— 建议直接用默认（不开这个开关）。
* **0.9 s 够不够，盲点路这次给了正面证据**：17:28 两次刷新在闸门后读到的都是**真词条**
  （槽1 `AR57突击步枪` → `AUG突击步枪` 判池内命中；槽2 `斯巴达B型防弹衣` → `旧D401型防弹衣` 池外），
  没有出现 17:05 那种「读到旧词条」的假结论。剩下要量的是动画窗口本身（见上）。
